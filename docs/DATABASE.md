# ZhanX DentalCare — Database

ZhanX DentalCare uses **PostgreSQL** as its single source of truth. The API is the only
component that connects to it; the desktop client never receives database credentials.

---

## 1. Connection

Connection details live in `<install>\.env` and are read only by the server:

```ini
DB_HOST=127.0.0.1
DB_PORT=5432
DB_NAME=zhanx_dentalcare
DB_USER=zhanx_app
DB_PASSWORD=<generated by setup-server.ps1>
DB_POOL_MAX=10
```

- The application role (`zhanx_app`) owns the database and does not need superuser rights.
- The `postgres` superuser is used only during installation (role/database creation and the
  `btree_gist` extension).
- Development uses port `55432` with a local cluster stored in
  `%LOCALAPPDATA%\ZhanX\dev-pgdata` (outside OneDrive); production uses the normal
  PostgreSQL service on `5432`. Start or stop it with `.\scripts\dev-db.ps1`; its log is
  `%LOCALAPPDATA%\ZhanX\logs\postgres.log`.

Check the connection:

```powershell
$env:PGPASSWORD="<db password>"
psql -h 127.0.0.1 -p 5432 -U zhanx_app -d zhanx_dentalcare -c "SELECT version();"
```

## 2. Schema overview

30 application tables plus `schema_migrations`.

### Core and security (001)

| Table | Purpose |
|---|---|
| `roles` | Administrator, Dentist, Receptionist, Dental Assistant |
| `permissions` | 35 permission codes grouped by module |
| `role_permissions` | Role → permission mapping |
| `users` | Staff accounts, bcrypt hash, lockout counters, `must_change_password` |
| `refresh_sessions` | Hashed, rotating refresh tokens (revocable sessions) |
| `clinic_settings` | Single row (`id = 1`) with clinic, billing, lab and backup preferences |
| `audit_logs` | Append-only audit trail (update/delete blocked by trigger) |
| `backup_history` | Every backup attempt, size, status and file path |

### Patients (002)

| Table | Purpose |
|---|---|
| `patients` | Demographics, `P000001` patient number, duplicate-warning fields |
| `patient_medical_history` | Allergies, conditions, medications, consent and notes |
| `documents` | Metadata for uploaded files (bytes live in `data/documents`) |

### Clinical (003)

| Table | Purpose |
|---|---|
| `appointments` | Day/week schedule, status, dentist, chair, reason |
| `appointment_status_history` | Every status transition with actor and timestamp |
| `consultations` | Draft → completed → amended clinical notes |
| `consultation_notes` | Amendment/addendum trail |
| `dental_chart_records` | FDI tooth findings, versioned with `is_current` |
| `tooth_conditions` | Condition catalog, color and tooth-type applicability |
| `treatment_catalog` | Services with default prices |
| `treatment_plans` / `treatment_plan_items` | Proposed vs completed treatment, discounts |
| `prescriptions` / `prescription_items` | Dentist-approved prescriptions and medicines |

### Billing (004)

| Table | Purpose |
|---|---|
| `invoices` | Header, totals, `amount_paid`, `outstanding_balance`, status |
| `invoice_items` | Line items with quantity, unit price, discount, tax |
| `payments` | Cash/UPI/card/bank/cheque collections with idempotency key |
| `refunds` | Refunds against an invoice, reason and approver |

### Inventory and labs (005)

| Table | Purpose |
|---|---|
| `inventory_items` | Materials, batch, expiry, purchase price, minimum stock |
| `stock_movements` | Purchase, consumption and adjustment movements |
| `suppliers` | Supplier directory |
| `dental_laboratories` | Lab directory (when the lab module is enabled) |
| `dental_lab_orders` | Lab work orders and status |

## 3. Data rules enforced by the database

### Money

- All amounts use `NUMERIC(12,2)`. No `float`/`double` columns exist for money.
- The API performs all arithmetic on **integer paise** using `BigInt`
  (`apps/server/src/utils/money.js`). Decimal strings from PostgreSQL are parsed
  directly, quantities are scaled integers, and every division rounds half-up once.
  No balance, line total, tax or refund amount is ever computed with floating point.
- `invoices.amount_paid` = completed payments − refunds; `outstanding_balance` is derived
  and constrained to be ≥ 0.
- Invoice status: `draft`, `issued`, `partially_paid`, `paid`, `void`.

### Immutability and audit

- `audit_logs` rejects `UPDATE` and `DELETE` (`audit_logs_no_update` trigger).
- `payments`, `refunds` and `consultations` reject `DELETE`; corrections use void,
  refund or amendment workflows.
- Invoices can only be deleted while `status = 'draft'`
  (`invoices_no_delete` trigger). Finalized invoices are voided, never deleted.
- `consultations` keeps the original content; amendments are appended with author and
  timestamp.

### Appointments

- `CHECK (end_time > start_time)`.
- An exclusion constraint prevents two **active** appointments for the same dentist from
  overlapping on the same date. Cancelled, no-show and completed appointments are excluded.

### Dental chart

- Findings are never overwritten. A new row is inserted and the previous row is marked
  `is_current = false`, with `superseded_at` and `superseded_by` recording who changed it.
- Tooth numbers are validated against FDI notation for permanent and primary dentition.

### Identifiers

- Primary keys are UUIDs (`gen_random_uuid()`), except high-volume history tables that use
  identity `bigint`.
- Human-readable numbers come from sequences: `P000001` (patients), `INV-2026-00001`,
  `PAY-000001`, `REF-000001`, `CONS-000001`, `TP-000001`, `RX-000001`, `LAB-000001`.

## 4. Roles and permissions

Permissions are enforced **on the server** for every route, not only hidden in the UI.
The client receives the caller's permission list after sign-in and uses it to render the
sidebar and action buttons.

| Module | Administrator | Dentist | Receptionist | Assistant |
|---|---|---|---|---|
| Dashboard | ✓ | ✓ | ✓ | ✓ |
| Patients | full | view/edit/medical/docs | create/edit/view/docs | view/docs |
| Appointments / queue | full | manage | manage | view queue |
| Consultations | full | create/complete/amend | — | view |
| Dental chart | full | view/edit | — | view |
| Treatment plans | full | manage | — | view |
| Prescriptions | full | manage | — | — |
| Invoices / payments | full | create/void, view | create/void, collect | — |
| Refunds | ✓ | — | — | — |
| Inventory | full | view | view | manage |
| Labs | full | manage | view | manage |
| Reports | all | operational + financial | operational | operational |
| Users, settings, backups, audit | ✓ | — | — | — |

Full permission codes are defined in `apps/server/src/config/permissions.js` and seeded
into `permissions` / `role_permissions`.

## 5. Migrations

Migration files live in `database/migrations` and run in filename order. Each file is
applied inside a transaction and recorded in `schema_migrations`.

```powershell
cd C:\ZhanX\Server\server
node src\database\migrate.js
```

Run migrations:

- during installation (`setup-server.ps1`),
- after every application update,
- never by editing an already-applied file — add a new numbered migration instead.

To create a migration, add `database/migrations/006_description.sql` and test it against a
copy of a real database first.

## 6. Seed data

Seeding has two modes:

| Command | What it does |
|---|---|
| `node src\database\seed.js` | Migrations + reference data (roles, permissions, tooth conditions, treatment catalog, default supplier/lab) + administrator if none exists |
| `node src\database\seed.js --demo` | Also inserts **development-only** demo patients, appointments and staff |

`setup-server.ps1` and `create-admin.js` call the first mode only. Production installations
therefore start with an **empty clinic database** and a securely created administrator.

Demo accounts (`dr.arjun`, `priya.front`, `kavya.assist`, password `Demo@12345`) exist
only after an explicit `--demo` run on a development machine. Never run `--demo` against
the clinic's production database.

## 7. Administrator account

```powershell
cd C:\ZhanX\Server\server

# create the first administrator (interactive password prompt)
node src\database\create-admin.js --username=admin --full-name="Clinic Administrator"

# reset an existing administrator's password and revoke all sessions
node src\database\create-admin.js --reset-password
```

Password policy is validated by the server. Hashes use bcrypt with cost 12. The password
is never written to logs or stored in plain text.

## 8. Maintenance

```sql
-- database size
SELECT pg_size_pretty(pg_database_size(current_database()));

-- unused indexes (review before removing anything)
SELECT relname, indexrelname, idx_scan
FROM pg_stat_user_indexes WHERE idx_scan = 0 ORDER BY relname;

-- active connections
SELECT usename, state, count(*) FROM pg_stat_activity
WHERE datname = current_database() GROUP BY 1,2;
```

- `VACUUM (ANALYZE)` runs automatically via PostgreSQL autovacuum; no manual schedule is
  required for a clinic-sized database.
- Keep PostgreSQL updated within the same major version.
- Never edit financial rows directly with SQL. Use the application workflows so the audit
  trail and balances stay correct.

See `BACKUP_RESTORE.md` for protecting this data.
