# ZhanX DentalCare — Licensing, Activation and Reinstalls

ZhanX DentalCare is licensed **offline** to one clinic computer. A license is a JSON
file signed by ZhanX Studio with an Ed25519 key and bound to the **Device ID** of the
clinic server installation. The application verifies the signature and the device
binding locally; no internet connection is used for activation or daily operation.

- The clinic server owns the license and enforces it for every API call.
- The desktop client never verifies or stores a reusable licensing secret.
- The private signing key is **never** inside the application, installer, server
  package, repository or clinic configuration.

---

## 1. Device identity

The Device ID (format `ZXDC-7A91-2F83-C4D8`) is generated by the clinic server from:

| Input | Source | Notes |
|---|---|---|
| Windows Machine GUID | `HKLM\SOFTWARE\Microsoft\Cryptography\MachineGuid` | Survives Windows updates |
| C: volume serial | `cmd /c vol C:` | Changes if the system disk is replaced/formatted |
| Installation secret | `data\device\installation.secret` | 32 random bytes generated on first run |

All values are normalized (lowercase letters and digits), concatenated with a version
prefix and hashed with SHA-256. The first 12 hex characters form the Device ID.
IP addresses and MAC addresses are deliberately **not** used: DHCP, Wi-Fi, VPN and USB
adapters change them routinely.

The installation secret is protected with **Windows DPAPI**. New installations use
`LocalMachine` scope so the scheduled task running as `SYSTEM` can read the same
identity as the administrator who activated it; older user-scoped secrets are migrated
in place on the next start without changing the Device ID. The secret is written
atomically with owner-only permissions. If DPAPI is unavailable the secret is stored
with file permissions only and a warning is logged. The Device ID is shown on the
activation screen and by `GET /api/license/status`.

If a machine identifier is missing, the Device ID is still derived from the remaining
values (the missing value is replaced by `-`). If the installation secret cannot be
decrypted or is corrupted, a new secret is generated, which yields a **new Device ID**
and requires a new license. This is intentional: a damaged activation can never
silently bypass licensing.

## 2. License file format

```json
{
  "format": "zhanx-license/1",
  "payload": {
    "licenseId": "LIC-20261029-EB28C0",
    "productId": "zhanx-dentalcare",
    "licenseVersion": 1,
    "deviceId": "ZXDC-5AC3-7387-81F6",
    "clinicName": "ZhanX Dental Clinic",
    "dentistName": "Dr. Arjun Mehta",
    "licenseType": "perpetual",
    "issuedAt": "2026-10-29T09:32:48.627Z",
    "expiresAt": null,
    "features": ["*"]
  },
  "signature": "<base64 Ed25519 signature>"
}
```

The signature covers `zhanx-license/1\n` followed by the **canonical JSON** of the
payload (object keys sorted, no insignificant whitespace). Verification order:

1. File size, JSON structure and format string.
2. Ed25519 signature against the embedded public key.
3. `productId` = `zhanx-dentalcare` and `licenseVersion` = `1`.
4. `deviceId` must equal this computer's Device ID exactly.
5. `expiresAt` (only for `subscription` / `evaluation`) must be in the future.

Any failure rejects the license. Failure reasons returned by the API:

| Reason | Meaning |
|---|---|
| `LICENSE_MISSING` | No license file on this server |
| `LICENSE_SIGNATURE_INVALID` | Signature, payload or format is invalid/tampered |
| `LICENSE_PRODUCT_MISMATCH` | License was issued for another product |
| `LICENSE_VERSION_UNSUPPORTED` | License format newer than this build |
| `LICENSE_DEVICE_MISMATCH` | License was issued for another Device ID |
| `LICENSE_EXPIRED` | Subscription/evaluation license has expired |
| `DEVICE_IDENTITY_UNAVAILABLE` | Windows identifiers could not be read |

## 3. Signing key management (publisher only)

The generator lives in `tools\license-generator` and is **not** included in the client
installer or the server package. The private key belongs offline.

Create a keypair once, on an offline publisher machine:

```powershell
node -e "const c=require('crypto'),f=require('fs');const {privateKey,publicKey}=c.generateKeyPairSync('ed25519');f.mkdirSync('tools/license-generator/keys',{recursive:true});f.writeFileSync('tools/license-generator/keys/private.pem',privateKey.export({type:'pkcs8',format:'pem'}));console.log(publicKey.export({type:'spki',format:'der'}).toString('base64'))"
```

- Store `private.pem` on encrypted offline media (two copies in separate locations).
- `tools/license-generator/keys/`, `history.json` and issued license files are ignored
  by git. Never commit, email or ship the private key.
- The public key is embedded as the default `ZHANX_LICENSE_PUBLIC_KEY` in
  `apps\server\src\config\env.js`. The same value can be supplied through `.env` on the
  server (useful for key rotation without rebuilding the server).
- The public key fingerprint can be printed with
  `node tools\license-generator\generate.mjs public-key`.

**Rotation.** Generate a new Ed25519 keypair, publish the new public key in the next
build (or set `ZHANX_LICENSE_PUBLIC_KEY`), then reissue licenses for all clinics. Older
licenses fail signature verification after rotation. Keep the retired private key only
as long as an audit/rollback policy requires.

## 4. Issuing a license

On the publisher machine:

```powershell
node tools\license-generator\generate.mjs issue `
  --device ZXDC-7A91-2F83-C4D8 `
  --clinic "Smile Dental Clinic" `
  --dentist "Dr. A. Kumar" `
  --address "12 MG Road, Kochi" `
  --contact "+91 98450 12345" `
  --type perpetual `
  --out licenses\smile-dental.json
```

Options:

| Option | Default | Notes |
|---|---|---|
| `--device` | required | Device ID shown in the app |
| `--clinic` | required | Clinic name recorded in the license |
| `--dentist` | empty | Dentist name recorded in the license |
| `--type` | `perpetual` | `perpetual`, `subscription` or `evaluation` |
| `--expires` | empty | Required for subscription/evaluation; ISO date |
| `--features` | `*` | Comma-separated feature flags |
| `--key` | `tools\license-generator\keys\private.pem` | Use an offline key path |
| `--out` | `license-<clinic>-<id>.json` | Output file |

Verify before sending:

```powershell
node tools\license-generator\generate.mjs verify --file licenses\smile-dental.json --device ZXDC-7A91-2F83-C4D8
```

Every issuance is appended to `tools\license-generator\history.json`; list it with
`node tools\license-generator\generate.mjs history`. Send the clinic **only** the JSON
license file.

The license payload carries the clinic name and dentist name for reference, but those
fields are not proof of authorization — only the signature and Device ID binding are.

## 5. Activation in the clinic

1. First launch shows the activation screen with this computer's Device ID.
2. The clinic sends the Device ID to ZhanX Studio and receives a signed license file.
3. The clinic enters clinic name, dentist name, address and contact number, imports the
   license file (or pastes the key) and clicks **Activate ZhanX DentalCare**.
4. The server verifies signature, product, version, device and expiry, writes the license
   atomically to `data\license\zhanx.license.json` (owner-only), records an audit entry
   `license.activate`, and saves the clinic details in `clinic_settings`.
5. The app then asks for the **initial administrator account**, and only after that
   opens the sign-in screen.

No patient, clinical, billing or administrative API is reachable before a valid license:
the server returns `403 LICENSE_REQUIRED` for every protected route, and sign-in/refresh
also refuse to issue sessions. The renderer cannot bypass this by changing its state —
authorization is recomputed on the server from the signed file and the current Device ID.

The license is re-read on every server start and cached for 20 seconds (invalidated when
the file changes), so replacing or removing the file takes effect immediately.

---

## 6. Expiry policy

- `perpetual` licenses have **no** expiry field and never introduce online checks.
- `subscription` / `evaluation` licenses carry `expiresAt`; after that date the server
  reports `LICENSE_EXPIRED`, the app shows the activation screen, and writes are
  refused. **Patient data is never deleted on expiry.**
- Renewal means importing a newly issued license file for the same Device ID; no data
  migration is needed.

## 7. Reinstalls, hardware changes and recovery

| Scenario | Device ID | Patient data | Action |
|---|---|---|---|
| Reinstall the desktop client | unchanged | untouched (server) | Nothing; sign in again |
| Reinstall the server package, keep `.env` and `data\` | unchanged | untouched | Nothing |
| Windows reinstalled on the server PC | new | untouched (PostgreSQL) | Reissue the license |
| System disk replaced / volume serial changed | new | untouched | Reissue the license |
| Motherboard swapped, Windows not reinstalled | usually unchanged | untouched | Reissue only if the Device ID changed |
| `data\device\installation.secret` lost/corrupted | new | untouched | Reissue the license |
| `data\license\zhanx.license.json` corrupted/deleted | unchanged | untouched | Re-import the same license file |
| Server restored to a new machine from a DB backup | new | restored | Reissue the license |
| DPAPI can no longer decrypt the secret (changed machine keyring) | new | untouched | Reissue the license |

If the license file is corrupted, the app fails closed and shows the activation screen —
it never falls back to an unlicensed mode. Re-importing the original license restores
access. Keep a copy of `data\license\zhanx.license.json` together with your normal
server-folder backup; the database backup (`pg_dump`) does not include it. Losing the
license is recoverable: ZhanX Studio can reissue it for the same Device ID from
`history.json`. Do not delete `data\device\installation.secret` unless a new Device ID
is intended.

**Reactivation:** open the activation screen (shown automatically when verification
fails), import the current license file, and click **Activate**. If the Device ID has
changed, request a new license quoting both the old and new Device ID and the license ID.

## 8. Per-workstation licensing

A license authorizes the **clinic server installation** whose Device ID it names.

- Front-desk PCs run the desktop client against that licensed server and do not each
  hold a license. If the server is not activated, they cannot read or write clinic data.
- Copying the server folder (including `data\`) to another PC yields a different Device
  ID, so the copied license is rejected. A second clinic server requires its own license.
- Do not deploy two independent servers under one license.

---

## 9. Offline licensing limitations

- **No revocation**: a signed license cannot be cancelled remotely. Expiry dates or
  reissue under a new key are the available controls.
- **Clock trust**: subscription expiry uses the local Windows clock. A deliberately
  rolled-back clock can extend a subscription; this is a known offline trade-off.
- **No usage telemetry**: the app never sends clinic or usage data to ZhanX Studio.
- **Physical access matters**: someone with administrator access to the server and the
  signing key could forge licenses — keep the private key offline and separate.
- **Obfuscation is not a security boundary**: the Electron bundle is readable; security
  rests on server-side verification and the private key never being distributed.

## 10. Verification performed

Automated tests (`cd apps\server; npm test`, 49 passing on 2026-10-29) cover:

- Missing license blocks protected APIs and sign-in with `403 LICENSE_REQUIRED`.
- Valid activation, clinic-detail persistence, restart persistence.
- Bad signature, modified payload and wrong-device licenses are rejected.
- Expired licenses are rejected; perpetual licenses carry no expiry.
- A missing/corrupted stored license fails closed and recovers after re-import.
- Replacing an existing license requires an authenticated administrator.
- The renderer cannot bypass backend authorization (direct API access is refused).
- Initial setup is available only with a valid license and zero users, then closes
  permanently; the first administrator can sign in and use administrative APIs.
